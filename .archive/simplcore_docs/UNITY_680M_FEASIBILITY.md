# 青小团 · 680M 专家训练可行性分析与架构优化设计

> 目标：在 AMD Radeon 680M（集成显卡）上，分领域训练 100M~200M 专家小模型并 SimplUnity 集成。
> 核心问题：**680M 够不够跑 6,000,000 步？** —— 结论：**单卡不可行，且不该跑这么多步**。
> 本文给出事实核算、瓶颈定位、以及"补 GPU 后端 + 重标定步数 + 容错续训"的可落地架构方案。

---

## 1. 一句话结论

| 问题 | 答案 |
|---|---|
| 680M 物理上能否跑 600万步？ | **不能**（显存/带宽/时间任一都超标） |
| 当前栈是否已用上 680M？ | **没有**——`simplcore.tensor` 是纯 NumPy CPU 后端，`cuda` 是空壳 |
| 600万步对 100M 字符模型有必要吗？ | **没有**——2万~10万步已饱和，600万是过拟合+浪费 |
| 正确路线？ | 补 OpenCL/ROCm GPU 后端 + 梯度检查点 + 容错续训 + 步数重标定到 2万~10万 |

---

## 2. Radeon 680M 硬件规格（实测/官方核对）

| 项目 | 规格 | 对训练的含义 |
|---|---|---|
| 架构 | RDNA2 (Rembrandt) | 支持 OpenCL 2.2 / Vulkan 1.3 |
| 计算单元 | 12 CU / 768 shaders | FP32 峰值 **3.4~3.7 TFLOPS** |
| 显存 | **2 GB 共享系统内存**（非独立显存） | 模型+优化器+激活必须 < 2GB |
| 内存总线 | 128-bit DDR5/LPDDR5 | 带宽 **76.8~102.4 GB/s**（DDR5-4800 / LPDDR5-6400） |
| TDP | 15~50W（可配） | 长训练需散热，否则降频 |
| Compute API | **OpenCL 2.2 可用**；ROCm 官方 **不支持** Windows/RDNA2 iGPU | 只能走 OpenCL，不能走 ROCm |
| 当前引擎后端 | 纯 NumPy **CPU** | 680M 完全闲置，等于拿 CPU 跑 |

**关键事实**：680M 在 Windows 下**没有 ROCm**，但有 **OpenCL 2.2**。`simplcore.tensor` 目前连 OpenCL 都没接，`cuda` 类只是 no-op（见 `tensor/__init__.py` 的 `_CudaCompat`）。

## 3. 600万步可行性核算（三个硬约束）

### 3.1 显存约束（最致命）
以 **100m 专家**（实测 ~148M 参数）为例，float32 占用：
- 参数：148M × 4B = **592 MB**
- AdamW 动量 m/v：2 × 592 = **1.18 GB**
- 梯度：592 MB
- 激活 + 计算图（12 层全量）：视 seq_len/batch，**300 MB~1 GB+**
- 语料/批处理缓冲：~100 MB

**合计轻松超过 2 GB 共享内存上限**。即便用梯度检查点，参数+优化器已占 ~1.8GB，余量不足以容纳 600万步的任何中间态序列。

> 200m 专家（~191M）更不可能。

### 3.2 带宽约束
每训练步需读写：参数(592MB) + 梯度(592MB) + 优化器状态(1.18GB) ≈ **2.4 GB/步** 仅权重搬运。
- 有效带宽取 80 GB/s（共享内存实际更低）：2.4GB / 80 = **30 ms/步 仅权重 IO**，未算计算。
- 600万步 × 30ms = **180,000 s ≈ 50 小时** 仅 IO，且这是理论下限（CPU 后端更慢 20~100x）。

### 3.3 时间约束（CPU 后端实测推断）
你之前在沙箱里 ~50 步就被强杀（属环境限制，但反映单步极慢）。保守估 NumPy CPU 单线程 **1~5 步/秒**：
- 600万步 ÷ 3步/s = **2,000,000 s ≈ 23 天**（单专家，不眠不休）
- 4 个领域专家 ≈ **3 个月**
- 中途任何崩溃 = 从头来（当前 save 不存 optimizer/RNG，无续训）

### 3.4 收敛约束（最该纠正的）
100M 字符级模型在真实中文语料（~7000 字/领域）上：
- 2000~20000 步 loss 已趋于平稳（你之前 15 步从 7.04 降到 6.75 已可见趋势）
- 600万步 = **300x 冗余**，必然严重过拟合，与"真实语料不要垃圾"目标相悖

> **结论**：600万步在 680M 上**物理不可行**，且**训练上无意义**。应重标定到 **2万~10万步 + 早停**。

## 4. 架构层面的真问题（比"够不够"更值得修）

读完 `lattice_model.py` / `expert_training.py` / `tensor` 引擎后，定位到以下缺陷：

| # | 问题 | 现状 | 影响 |
|---|---|---|---|
| 1 | **无 GPU 后端** | `tensor` 仅 NumPy CPU；`cuda` 是空壳 | 680M/独显全废，纯 CPU 慢 20~100x |
| 2 | **无梯度检查点** | 12 层全量建图，内存随层数线性爆 | 100M 都装不下 2GB |
| 3 | **无容错续训** | `save` 只存参数，不存 optimizer/memory_state/RNG/step | 崩了从头来，600万步不可想象 |
| 4 | **HashMemory 每步全量 clone** | `flat_mem = memory.reshape(...).clone()` | 每步多 O(B·C·S·D) 拷贝 |
| 5 | **RC 用 gather 复制窗口** | `h[:, win, :]` 复制 (B,L',K,D) | 序列长时内存翻倍 |
| 6 | **AdamW 用 `id(p)` 做 state key** | 跨进程/续训后 id 变化 | 续训动量丢失 |
| 7 | **无混合精度** | 全 float32 | 显存/带宽翻倍浪费 |
| 8 | **无数据分片/流式** | 全量语料进内存再滑窗 | 大模型无法扩展 |

## 5. 优化架构设计（可落地）

### 5.1 GPU 后端抽象（让 680M 真正参与）
```
simplcore/tensor/
  backend.py          # 现有 NumPy 后端
  backend_opencl.py   # 新增：OpenCL 2.2 封装（cl.Buffer / enqueue ND range）
  backend_selector.py # 新增：探测 OpenCL → 降级 NumPy
```
- 算子层（matmul/einsum/conv）走 OpenCL kernel；归约/索引走 CPU 回读。
- `cuda` 壳改为 **OpenCLDevice** 兼容接口，保留 `is_available()`、`memory_allocated()` 真实实现。
- **注意**：OpenCL 在 680M 上做 autograd 反向 kernel 工程量大；务实做法是**前向+矩阵乘上 GPU，反向用重计算（梯度检查点）在 CPU 回放**——避免写全套 GPU 反向 kernel。

### 5.2 梯度检查点（内存降 40~60%）
- 接入已有的 `tensor/utils/checkpoint.py`。
- `LatticeBlock.forward` 改为 `checkpoint(recompute=True)`：只存块输入，反向时重算块内。
- 12 层 → 激活内存从 O(12·L·D) 降到 O(L·D + 12·输入)。

### 5.3 容错续训（关键，让长训练可能）
- `ExpertTrainer.save` 扩展存：`optimizer.state_dict()` + `memory_state` + `rng.getstate()` + `step` + `loss_history`。
- `load` 恢复全部状态，`--resume` 从断点继续。
- checkpoint 落盘频率可配（如每 500 步 + 末步），保证崩了只丢 <500 步。

### 5.4 HashMemory / RC 内存优化
- HashMemory：`np.add.at(flat_mem, flat_idx, val)` **原地 scatter**，去掉 `.clone()` 全量拷贝。
- RC：用 `np.lib.stride_tricks.sliding_window_view` 替代 `gather` 复制窗口，零拷贝滑窗。

### 5.5 混合精度 + 参数分组
- 权重/激活用 float32（NumPy 无真 bfloat16）；但**梯度用 float16 累加 + float32 更新**可省一半带宽。
- AdamW `state` key 从 `id(p)` 改为**参数名 `name`**（Module 已支持 `named_parameters`），续训不丢动量。

### 5.6 步数重标定（文档明确纠正）
- 默认 `total_steps=20000`，加**早停**（loss 连续 N 步不降则停）。
- 600万步标注为"需多卡 GPU 集群的远期目标"，680M 单卡只跑子集验证架构正确性。

## 6. 重标定后的可行性（乐观估算）

假设完成 5.1~5.5 优化，680M OpenCL 后端（取保守 1 TFLOPS 有效算力 + 50 GB/s 带宽）：

| 专家 | 参数 | 显存(检查点+fp16 grad) | 每步时间 | 2万步耗时 |
|---|---|---|---|---|
| 100m | 148M | ~1.1 GB ✓ | ~40 ms | **~13 分钟** |
| 200m | 191M | ~1.4 GB ✓ | ~60 ms | **~20 分钟** |
| 4 专家合计 | — | — | — | **~1.5 小时** |

> 对比原 600万步方案（23天/专家），**提速 ~1000x**，且显存可容纳。

## 7. 实施优先级（若后续要落地）

1. **P0**：容错续训（save/load 全状态）+ 早停 —— 不依赖 GPU，立刻让长训练可恢复。
2. **P0**：HashMemory/RC 内存优化 —— 立刻降低显存峰值。
3. **P1**：梯度检查点接入 —— 让 200m 在 2GB 内可行。
4. **P1**：OpenCL 后端（前向+matmul）—— 让 680M 真正加速。
5. **P2**：混合精度梯度 —— 再省一半带宽。
6. **P2**：步数重标定 + 文档纠正 600万步目标。

---

## 8. 最终答复

**680M 够不够跑 600万步？**
- **不够，且不该跑。** 显存(2GB共享)装不下单个 100M 专家的训练态；CPU 后端跑完需 23天/专家；600万步对字符模型是 300x 冗余过拟合。
- 当前栈甚至**没用上 680M**（纯 NumPy CPU），`cuda` 是空壳。
- 正确路线：**补 OpenCL GPU 后端 + 梯度检查点 + 容错续训 + 步数重标定到 2万~10万**。完成优化后，4 个 100~200M 专家可在 **~1.5 小时** 内于 680M 上训完，显存可控。

> 本文为可行性分析文档，未修改任何运行代码。如需落地第 7 节的优化，请确认后端路线（OpenCL 优先）与步数重标定，我再动手实现。
