# O(1) 状态的检索容量账（原创点 B 的起点）

> 对应 `SimplCore-原创贡献清单.md` 的 **B**。代码：`simplcore/core/retrieval_bound.py`；
> 测试：`test_retrieval_bound.py`。这不是定理，是一个**把两个问题拆开**的可证伪框架。

## 1. 先拆开"压缩比"和"可寻址性"

论文 §5.12 的论证是：1M token 原文 ≥ 2 GB，状态 30.4 MiB，压缩比 1:67 且有损
→ 精确检索必输。

这个论证**在信息论上不成立**。按 `tuan-1b` 实算：

| 项 | 值 |
|---|---|
| 状态浮点数（`stream_state_bytes/4`） | ≈ 7.96M floats |
| 按有效尾数 24 bit 计 | ≈ 1.91e8 bit |
| 1M 个 (key, value)，V=32000，各 15 bit | ≈ 3.14e7 bit |
| **容量比** | **≈ 6.1×** |

也就是说：**比特数是够的**。30.4 MiB 不是"装不下 1M 个 key"，
而是"装下了却没法按 query 随机取某一个"。

## 2. 真正的瓶颈：固定维线性读出

SGC / Mamba / RWKV / GLA 的状态读出都是**固定维线性/低秩映射**：
`y = Σ_i (q·k_i) v_i`。它没有哈希表那种"按 key 定位槽位"的能力。
对 S 维各向同性 key、L 个 key，单个目标相对其余 L−1 个的干扰：

```
SNR ≈ sqrt(S / (L−1))
```

`tuan-1b` 全状态（7.96M floats）对 L=1M：**SNR ≈ 2.8**；单层状态
（`2·M·D = 524k` floats）对 L=1M：**SNR < 1**（干扰淹没）。
这解释了为什么"层数越多、检索越好"，也解释了为什么单层探针（D=48）做不出结论。

## 3. 可证伪预测

- 若 needle 成功率随 `S/L` 呈 **SNR 量级的饱和曲线**（而非随 S 线性上升），
  支持"容量够、读出结构是瓶颈"；
- 若实测成功率**显著高于** SNR 预测（例如 S/L=0.5 时仍 >0.9），
  说明模型学到了非线性内容寻址，本框架必须修；
- 若把状态从 fp32 降到 bf16（bits_per_float 24→8），容量比降到 ~2×，
  但 SNR 不变 —— 预测"降精度主要伤容量、不伤寻址"，可单独测。

## 4. 诚实的边界

- 这是**条件界**，不是定理：key 独立各向同性、value 需要 log2(V) bit、
  读出线性 —— 三条假设缺一不可；
- 它不预测具体成功率，只给量级/趋势；
- 1M needle 的实测仍需 GPU（原创点 D），当前框架只负责把"容量论证"从
  论文里剔除，避免用错误的理由支持正确的结论。
