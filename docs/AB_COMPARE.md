# SGC vs Attention：受控 A/B 的方法与本次实测

> 这份文档记录的是**一次具体的对照实验**，不是架构主张。
> 它存在的目的是让"1B 抵 3B~7B"这类说法要么被证据支持，要么被证伪 ——
> 而不是永远停在"理论上更省"。

---

## 0. 一句话结论

**本轮 A/B 的差异不显著，不能据此声称 SGC 优于 attention。**

而且它给出了两个更值得注意的现象：

1. **通过率与验证损失给出相反的排序**（A 通过率高，B 验证损失低）；
2. **训练 FLOPs 与墙钟给出相反的排序**（A 少 15% FLOPs，却多 13% 墙钟）。

这两条都不是"测量噪声"，而是两个不同的东西被同一个数字掩盖了。
下面逐条说明。

---

## 1. 为什么要专门写一套 A/B

### 1.1 最常见的失败不是"结论错"，是"两边根本不可比"

对照实验最容易出的问题，都是"看起来在比，其实没比"：

| 失败模式 | 表现 | 为什么难发现 |
|---|---|---|
| 一边多训了 token | 差 5~10% 的 token，赢的那侧恰好是多的那侧 | 报告里只有 pass rate |
| 梯度累积口径不同 | 长样本被系统性低估 | loss 曲线都好看 |
| 词表从验证集统计 | 验证损失偏低 | 只会觉得"泛化不错" |
| 评测侧解码策略不同 | 一侧贪心、一侧采样 | 两侧都能"跑通" |
| 参数量差 30% 还叫"同规模" | 差异被算成架构优势 | 没人去核对 `num_params()` |

所以 `sft.py` 只提供一个 `train_sft`，`ab_compare.py` 把除 mixer 之外的一切
都钉死，`fairness_report()` 在出结论前先自检。

### 1.2 固定了什么

| 固定项 | 做法 |
|---|---|
| 数据 | 同一份 JSONL，按**行号**切 train/val（0..n_train / n_train..n） |
| 词表 | 同一份 `CharVocab`，且**只从训练段统计**（不看验证段） |
| 模板 / 掩码 / 打包 | 同一个 `ChatTemplate` + 同一个 `SFTDataset` 实现 |
| 超参 | 同一个 `SFTConfig` 实例（lr、warmup、clip、batch、grad_accum 全同） |
| 评测 | `BASIC_DIALOGUE_SUITE`，**贪心解码**（`temperature=0`） |
| 唯一变量 | `mixer`：`sgc` vs `attn` |

## 2. 本次实测（CPU，`--smoke --match params`）

```bash
python scripts/ab_compare.py --smoke --match params --max-steps 300 \
    --out-dir runs/ab_smoke
```

### 2.1 两侧配置

| 项 | A（sgc） | B（attn） | B/A |
|---|---|---|---|
| 总参数 | 2,481,684 | 2,705,664 | **1.090×** |
| 非嵌入参数 | 2,399,764 | 2,623,744 | 1.093× |
| 嵌入占比 | 3.3% | 3.0% | — |
| 宽度 / 层数 | 256 / 4 | 256 / 4 | 同 |
| 每 token 训练 FLOPs | 0.0147 G | 0.0173 G | **0.847×** |
| 训练 token | 70,875 | 70,875 | 1.000× |
| 步数 | 300 | 300 | 1.000× |
| 墙钟 | **190.9 s** | **169.3 s** | 1.128× |

`fairness_report()` 判定 `comparable = True`（无违规：步数、token、提前停止、
非有限 loss 全部一致）。参数量差 9.0% 落在"整数层数量化"的粒度内 ——
同宽度下 1 层差约 25%，所以 9% 已经是最接近的可达点。

### 2.2 结果

| 指标 | A（sgc） | B（attn） | 谁更好 |
|---|---|---|---|
| `task_pass_rate` | **0.700** | 0.500 | A |
| `stop_rate` | **1.000** | 0.600 | A |
| `turn_leak_rate` | 0.000 | 0.000 | 平 |
| **验证损失** | 0.2782 | **0.2106** | **B** |

配对统计：

```
Δpass      = +0.2000
95% CI     = [-0.2000, +0.6000]      ← 跨 0
McNemar    = (b=3, c=1), p = 0.6250  ← 不显著
翻转题数    = 4 / 10
```

翻转明细：

| 题目 | A | B |
|---|---|---|
| `greet` | 过 | 不过 |
| `self_intro` | 过 | 不过 |
| `length_limit` | 过 | 不过 |
| `multi_turn_ref` | 不过 | 过 |

### 2.3 这个 Δ 有多大信息量

10 道题、4 题翻转、分裂 3:1。在 H0（两种架构逐题通过概率相同）下，
4 次翻转里出现 3:1 或更极端的概率是 **0.625**。

反过来说：**这个套件要给出显著结果，至少需要 8:1 的分裂**（p≈0.039）。
换句话说，`+0.2` 的差值在这套评测上**连方向都不能确定**。

这不是"框架不够好"，而是 10 道题的信息量上限。要真正比较，
必须扩到「几百道规则可判的题」，或者改用验证损失的连续指标做配对比较。

## 3. 两个"排序相反"，各自意味着什么

### 3.1 通过率高、验证损失反而差

A 在格式行为上明显更好：`stop_rate` 1.000 vs 0.600。这直接导致
`greet` / `self_intro` / `length_limit` 三题翻转——那三题的失败原因
全是"该停没停、答太长"。

但 A 的验证损失更差（0.2782 vs 0.2106）。

**两者测的不是一件事：**

* `task_pass_rate` 测的是**格式服从**：能不能在正确的位置停下、
  能不能守住字数与符号约束。这是"对话可用性"的下限。
* 验证损失测的是**对数据分布的拟合**。它可以在格式一塌糊涂的情况下
  很低——只要模型把高频 n-gram 的边际分布学准了。

小模型、少步数的条件下，这两者会**脱钩**：attention 的 softmax 混合
更容易压低平均 NLL，但它对"什么时候该输出 `<|end|>`"这种**离散决策**
不一定更敏感。

**所以两个指标必须同时报。** 只报 pass rate 会高估 A，只报 val_loss
会高估 B，而且两次高估都能自圆其说。

### 3.2 FLOPs 少、墙钟反而慢

A 每 token 训练 FLOPs 比 B 少 15.3%，但墙钟多 12.8%。

原因不在架构，在**实现**：

* SGC 的训练路走 `irfft(rfft(x,2L) · rfft(K_pad,2L))[:L]`。在 CPU 上，
  长 128 序列的 FFT 调用开销 + 频域逐元素乘的内存往返，
  不一定比 `L²` 的小矩阵乘更快（`L=128` 时 `L²` 只有 16k 次乘加）。
* attention 走的是高度优化的 `scaled_dot_product_attention` / `baddbmm`，
  这两个在 CPU 上有专门的内核。

**结论的边界**：FLOPs 优势是**解析层面**成立的；墙钟优势要么需要
更长的序列（FFT 的 `O(L log L)` 才压得过 `O(L²)`），要么需要
CUDA 上的定制内核（或直接做 IIR 递推训练）。

这一条必须写进任何"更省"的宣称里，否则就是把解析账本当成了实测。

## 4. 参数效率比：什么时候能报，什么时候不能

`param_efficiency()` **拒绝**在只有两个规模点时给比值：

```json
"caveats": ["每种架构至少需要两档参数量才能插值；当前不足以给出效率比。"]
```

这是刻意的。要把"1B 抵 3B"变成数字，需要：

1. **每种架构至少 3 档**参数量实测（例如 15M / 30M / 60M）；
2. 同一份数据、同一 token 预算、同一评测；
3. 在同一套题上做插值，找到"低参模型达到的分数对应多少参数量的高参模型"；
4. 报**内插**区间，不外推。

单点数据只能报"该点上的比值"，那是**一个模型的两个数字**，
不是效率曲线。把它说成曲线就是在编。

## 5. 杀灭条件（什么结果算失败）

跑正式 A/B 之前先把"什么算输"写死，避免事后解释：

| # | 条件 | 结论 |
|---|---|---|
| K1 | 同参数量、同 token 下，SGC 的 `task_pass` 比 attention **低 5 个点以上**且显著 | SGC 在对话任务上**没有**优势，撤回"抵 3B"说法 |
| K2 | 同 token 下 SGC 的验证损失持续更高（≥3 个 eval 点） | 拟合效率不如 attention，长上下文优势无法弥补 |
| K3 | `stop_rate` / `turn_leak_rate` 任一低于 attention | 格式层先失守，"能对话"的前提不成立 |
| K4 | 30M 的 `task_pass` 在三档参数量上都不随规模上升 | 缩放假设不成立，问题在数据或训练配方，不在架构 |
| K5 | 换成真实 SFT 数据后，两侧差距从 \|Δ\|>0.2 缩到 <0.05 | 合成数据上的差异是模板伪影，不受支持 |

K5 特别重要：本次用的是**模板化合成数据**，格式类任务占比刻意偏高。
真实对话数据的格式分布完全不同，A 侧在 `stop_rate` 上的优势有可能
一大部分来自"模板让停止位置极其可预测"。

## 6. 怎么跑

```bash
# CPU 自证（验证框架与统计链路，约 6 分钟）
python scripts/ab_compare.py --smoke --match params --max-steps 300

# 真机（需自备 data/sft_zh.jsonl）
python scripts/ab_compare.py \
    --preset-a tuan-30m --preset-b attn-30m --match params \
    --train-jsonl data/sft_zh.jsonl \
    --seq-len 1024 --batch 32 --max-steps 20000 --device cuda \
    --out-dir runs/ab_30m

# 三档规模扫参数效率（需要各跑一次，然后用 param_efficiency 汇总）
for N in 15000000 30000000 60000000; do
  python scripts/ab_compare.py --target-params $N --match params \
      --train-jsonl data/sft_zh.jsonl --out-dir runs/ab_$N
done
```

`report.json` 里必须一起看的三块：

* `meta.fairness` —— 两侧是否真的可比；
* `meta.param_gap` —— 参数量实际差多少（及其原因）；
* `pairs[0].evidence_weight` —— 有几题翻转（决定这个 Δ 能不能读）。

## 7. 与 `DREAMING_CMT.md` / `SGC_SPEC.md` 的关系

* `SGC_SPEC.md` 定义算子与闸门数学，**不**包含能力主张；
* `DREAMING_CMT.md` 定义自进化流程，其 no-regression gate 用的是
  `paired_bootstrap_ci`（同一套统计思想，但判的是"改完有没有变差"）；
* **本文档**是唯一允许出现"哪个更好"的地方，且必须带 `evidence_weight`。

任何把本文档的 `+0.2` 单独摘出来当结论的引用，都是误读。
